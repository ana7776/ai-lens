글을 다 썼다는 안도감이 드는 순간이 실수가 가장 많이 남아 있는 순간이기도 합니다. 특히 AI의 도움을 받은 글은 문장이 매끄러워서, 확인하지 않은 숫자나 경험처럼 쓰인 일반론이 그대로 공개되기 쉽습니다. 공개된 뒤에 발견한 오류는 고칠 수는 있지만, 이미 읽은 독자의 신뢰까지 되돌리기는 어렵습니다. 이 글은 발행 직전의 마지막 점검만 다루며, 업무 문서를 원자료와 대조하는 자세한 방법은 [문서 초안 검수 8단계](/work/ai-review-checklist/)에서 설명합니다. 다섯 영역의 점검 항목과 시간이 없을 때의 최소 점검을 차례로 정리했습니다. 다 읽으면 지금 발행하려던 글에 바로 적용할 수 있는 점검 순서를 갖게 됩니다.

## 검수의 책임 범위를 먼저 정합니다

AI에게 초안을 맡겼다는 사실이 결과의 책임을 대신해 주지는 않습니다. 발행하는 사람이 사실과 권리를 확인하고, 필요하면 원자료를 만든 사람이나 담당자에게 다시 확인합니다. 혼자 운영한다면 "발행 버튼을 누르는 나 자신이 마지막 확인자"라는 것을 기억하면 됩니다.

## 1. 사실 검수

- [ ] 날짜·숫자·이름·고유명사가 원자료와 일치한다
- [ ] 가능성이나 제안이 확정된 사실처럼 바뀌지 않았다
- [ ] 바뀔 수 있는 정보(요금, 기능, 정책)에 확인 기준일이 있다
- [ ] "항상", "모든", "반드시" 같은 표현에 근거가 있다

## 2. 출처 검수

- [ ] 인용문과 통계의 원출처를 직접 열어 확인했다
- [ ] 링크가 실제로 열리고 같은 내용을 담고 있다
- [ ] 출처의 범위(대상·기간)보다 넓게 쓰지 않았다
- [ ] 확인하지 못한 내용은 빼거나 확인 필요로 표시했다

AI가 알려준 링크는 존재하지 않거나 다른 내용일 수 있으므로, 붙여넣기 전에 반드시 열어봅니다.

## 3. 권리와 개인정보 검수

- [ ] 글에 다른 사람의 이름·연락처·사적인 내용이 남아 있지 않다
- [ ] 스크린샷에 이메일 주소, 알림, 계정 정보가 보이지 않는다
- [ ] 이미지·음원·폰트의 사용 조건을 확인했다
- [ ] 다른 글을 길게 옮겨 오지 않았고, 인용은 출처를 밝혔다
- [ ] 실존 인물이나 기관에 대해 오해를 만들 표현이 없다

## 4. 표현 검수

| 확인할 것 | 예시 | 고치는 방향 |
|---|---|---|
| 경험처럼 쓰인 일반론 | "직접 써보니 효과가 컸다" | 실제 경험이 아니면 일반 설명으로 |
| 결과를 보장하는 말 | "이 방법이면 무조건 해결" | 조건과 한계를 함께 |
| 같은 말 반복 | 앞 문단을 표현만 바꿔 다시 | 한쪽 삭제 |
| 제목과 본문의 불일치 | 제목은 "10가지", 본문은 7가지 | 제목이나 본문 맞추기 |

## 5. 화면과 사용성 검수

- [ ] 휴대폰에서 글을 처음부터 끝까지 읽어 봤다
- [ ] 표가 화면 밖으로 넘치지 않는다
- [ ] 내부 링크가 올바른 글로 연결된다
- [ ] 이미지에 대체 텍스트가 있다
- [ ] 글 마지막에 독자가 다음에 할 일이나 읽을 글이 있다

## 시간이 없을 때 최소 점검

모든 항목을 매번 확인하기 어렵다면, 오류가 났을 때 피해가 큰 세 가지만이라도 확인합니다.

1. **숫자와 날짜:** 원자료와 대조합니다.
2. **출처 링크:** 직접 열어봅니다.
3. **개인정보:** 본문과 이미지를 훑어봅니다.

나머지 항목은 발행 후 하루 안에 다시 확인하고, 고친 내용이 있다면 수정 기록을 남깁니다.

## 수정 기록 남기기

발행 후 내용을 고쳤다면, 의미 있는 변경은 글에 수정일과 무엇을 바꿨는지 표시합니다. 오탈자 수정처럼 사소한 변경은 기록하지 않아도 되지만, 숫자·사실·권장 사항이 바뀌었다면 독자에게 알리는 것이 좋습니다. 내용은 그대로 둔 채 날짜만 최신으로 바꾸는 일은 하지 않습니다.

## 사람의 편집을 남깁니다

검수를 통과한 글이라도 AI 문장을 이어 붙인 것에 그친다면 독자가 이 글을 읽을 이유가 약합니다. 마지막으로 이 글에 내가 더한 것이 무엇인지 한 문장으로 적어 봅니다. 직접 만든 예시, 정리한 표, 실제로 겪은 문제와 해결 과정처럼 다른 글에서 볼 수 없는 부분이 있는지 확인합니다.

검수 체크리스트는 형식적인 절차가 아니라, 반복 작업을 안전하게 만드는 운영 도구입니다. 같은 순서로 확인하는 습관이 누락을 줄입니다.
